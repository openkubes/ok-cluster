# OK-136 `ok-iot` runtime result — 2026-08-04

## Result

The approved `ok-iot` runtime created a functional Talos cluster and proved
KubeVirt placement on `ok-gpu`, but it did **not** satisfy the production
two-replica Longhorn acceptance criterion. The cluster remains running pending
a separate storage decision or Cleanup-GO.

- bootstrap wall time: 250.12 seconds;
- CAPI Available milestone: 246 seconds after namespace creation;
- both workload Nodes Ready: 244 seconds after namespace creation;
- Talos v1.9.6, Kubernetes v1.34.1 and Cilium 1.19.6;
- Cilium DaemonSet: desired/current/ready `2/2/2`;
- control-plane VMI: `ok-gpu`, 2 vCPU, 4 GiB, Running;
- worker VMI: `ok-gpu`, 4 vCPU, 8 GiB, Running;

- both DataVolumes Succeeded using local CDI clones from

- the Golden PVC remained Bound with UID
  `60b69267-e507-416a-b5a8-835bb0232ce6`.

## Failed storage acceptance

Both Longhorn volumes requested `numberOfReplicas: 2`, but each had only one
running replica on `ok-gpu` and reported `robustness: degraded`. Longhorn
reported `ReplicaSchedulingFailure: insufficient storage; precheck new replica
failed` for the missing replica on `ok-infra`.

The relevant live Longhorn bounds were:

- `storage-minimal-available-percentage`: 15;
- `storage-over-provisioning-percentage`: 100;
- `ok-infra` storage maximum: 497,238,532,096 bytes;
- `ok-infra` storage reserved: 149,171,559,628 bytes;
- `ok-infra` storage scheduled: 342,523,641,856 bytes;
- remaining scheduler budget: 5,543,330,612 bytes;
- requested aggregate boot-volume budget per replica, including the bounded
  filesystem-overhead allowance: 59,055,800,320 bytes.

Host filesystem free space was therefore not the limiting value. Longhorn's
reserved and already scheduled capacity made `ok-infra` ineligible for the
second replica.

## Guard correction

The original OK-136 preflight looked only at `storageAvailable` and therefore
produced a false PASS. The runtime-evidence path also verified the requested
replica count but not actual replica health and placement. The branch was
hardened after this observation:

- preflight now applies Longhorn reserved, scheduled, minimum-free-space and
  over-provisioning scheduler bounds;
- runtime evidence now requires `healthy` attached volumes and the reviewed
  number of running replicas on distinct Longhorn nodes;
- the stale locally generated PASS evidence was removed;
- offline tests reproduce the observed capacity numbers and reject degraded
  volumes.

The corrected live preflight now fails closed with:

```text
FAIL Longhorn capacity/placement is insufficient:
requested_per_replica=59055800320B
eligible=[{'name': 'ok-gpu', 'schedulable_bytes': 853139521946}]
```

No Longhorn settings, reservations, existing volumes or cluster resources were
changed as part of this correction.

## Read-only capacity inventory

A follow-up inventory found no `Released` PVs: every visible
`ok-storage-block` PV was `Bound`. One detached Longhorn scratch volume had no
PV reference, but its scheduled replica was on `ok-gpu`; removing it would not
increase the constrained `ok-infra` scheduler budget. There was therefore no
unambiguously safe cleanup capable of satisfying the missing replicas.

Recovery requires a separate, explicitly approved infrastructure decision:
retire identified disposable workload-cluster volumes, add eligible Longhorn
capacity, or deliberately revise the `ok-infra` reservation policy. The
running `ok-iot` resources were left unchanged.
